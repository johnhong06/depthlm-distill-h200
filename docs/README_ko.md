### 교사 추론 결과가 학습까지 어떻게 전달되는가

교사 추론이 가장 비싼 단계다(풀 하나당 44,800 px, 처음부터면 약 3 시간). 그 결과가 학습 작업까지 살아 있어야 하므로 세 곳에 두고, 학습은 이 순서로 찾는다.

1. `/app/output/labels/<pool>/teacher_labels.parquet` — 결과 원본 (완전본 23 MB)
2. `/app/data/labels/<pool>/teacher_labels.parquet` — `/app/data` 가 쓰기 가능하면 데이터 옆에 두는 사본. `/app/output` 이 다음 파드로 넘어오지 않아도 학습이 여기서 읽는다
3. `pools/<pool>/teacher_labels.parquet` — 저장소에 커밋된 라벨. 모든 파드가 무조건 갖고 있다

`/app/output` 도 `/app/data` 도 작업 사이에 남지 않는 환경이면, 라벨링이 끝난 뒤 `labels_<pool>.zip` 을 내려받아 `pools/<pool>/teacher_labels.parquet` 로 커밋한다. 라벨링 작업이 이 안내와 파일 크기를 찍는다. `train` 은 라벨을 못 찾으면 찾아본 세 경로를 모두 적어 주고 멈추며, 라벨이 격자에 필요한 픽셀을 다 덮지 못해도 멈춘다. `label` 을 다시 내면 이미 있는 것을 base 로 이어서 라벨링한다.

- 같은 명령을 다시 내면 이어서 돈다. 끝난 셀·평가·라벨 조각은 건너뛰므로 중간에 끊긴 작업은 빠진 부분만 한다. `/app/output` 을 비우면 처음부터다.
- `train` 은 라벨이 빠진 픽셀이 있으면 시작을 거부하고 라벨링할 풀을 알려준다. `eval` 은 어댑터가 없으면 거부하고 학습 명령을 알려준다.
- `grid <pool> <cond>`(학습+평가)와 `all`(전체)도 그대로 있지만 공용 파드에서는 권장하지 않는다. 2026-09 의 `all` 실행은 35 시간 뒤 강제 종료됐고 로그로는 어디까지 됐는지 알 수 없었다.
- **`/app/output` 은 결과 전용이다.** 압축 해제본·모델 캐시·임시 파일은 절대 넣지 않는다. 2026-09-27 에 `/app/output` 이 100 GB 를 넘겨 실험이 강제 종료됐고, 원인은 읽기 전용이던 `/app/data` 때문에 30 GB 짜리 해제본과 7.5 GB 학생 캐시가 `/app/output` 으로 갔던 것이다.
- **압축 해제 자체는 피할 수 없다.** `transformers` 와 이미지 로더가 파일 경로로 읽기 때문이다. 해제 위치는 이 순서로 고른다: `/app/data` 가 쓰기 가능하면 tar 조각 옆 제자리(사본 0) → `/app/scratch`(파드 작업 볼륨) → 컨테이너 임시 디스크. `/app/output` 은 명시해도 거부한다.
- **2026-09-28 파드 실측.** `/app/data` 는 읽기 전용이고 여유 103 GB, 사용 265 GB. `/app/output` 은 쓰기 가능, 여유 103 GB. 둘의 여유가 같으니 같은 볼륨이고, 2026-09 에 넘친 볼륨이 이것이다. `/app/scratch` 는 별도 볼륨으로 여유 950 GB이고 파드가 저장소를 clone 하고 `HF_HOME` 을 두는 곳이다. 그래서 해제본은 여기로 간다. `/app/data` 쓰기 권한은 요청할 필요가 없다.
- **`/app/scratch` 는 작업 사이에 유지되지 않는다 (2026-09-28 실측).** 한 작업이 `/app/scratch/h200_work` 에 풀어 놓았는데 다음 작업이 그것을 못 찾고 다시 풀었다. 저장소도 작업별 폴더로 clone 되고 `peft` 도 매번 다시 설치된다. 모든 작업이 빈 작업 볼륨에서 시작한다고 보면 된다.
- **`/app/output` 도 작업 사이에 넘어가지 않는다 (2026-09-28 실측).** 한 작업이 indoor 교사 라벨을 썼는데 한 시간 뒤 다음 작업이 본 `/app/output` 은 사용 0 GB 이고 자기 결과 파일 하나뿐이었다. 작업마다 결과 볼륨이 새로 생기고, 끝난 뒤 관리자가 그 작업의 파일을 꺼내 준다.
- **한 작업이 만든 것은 다음 작업이 보지 못한다.** 저장소가 유일한 영속 경로다. 그래서 라벨링이 끝날 때마다 `pools/<pool>/teacher_labels.parquet` 로 커밋해야 하고, 학습과 평가는 한 작업 안에서 돌려야 한다. `train` 다음에 `eval` 이 아니라 `grid <pool> <cond>` 를 쓴다. 작업을 쪼개는 방식은 결과 볼륨이 유지되는 환경, 예를 들어 로컬 장비에서만 쓸 수 있다.
- **그래서 해제는 매 작업의 일부이고, 값이 싸다.** 30 GB 가 약 2 분이다. 각 단계는 자기가 읽는 것만 푼다: `label` 29.5 GB(약 2 분), `train` 5.5 GB(약 22 초), `eval` 0.4 GB(약 2 초). `data` 를 두 번 이상 낼 이유는 없다. 조각 16개가 검증되고 풀리는지 한 번 확인하는 용도다.
- 비밀 없음(기본): 30 GB tar 를 2 GB 조각 16개로 나눠 드라이브로 전달. 관리자는 `/app/data` 아래 아무 폴더에 받아 두기만 하면 된다(조각 그대로든 드라이브가 만든 zip이든). `bash run.sh data` 가 조각을 찾아(zip 안이면 흘려 넣으며) SHA256 검증 후 조각 옆 제자리에 한 번 풀고, 이후 작업은 그것을 재사용한다(이미지 6 GB + 교사 가중치 24 GB, FAIR 라이선스 사본 동봉 = 1.b.ii). 해제가 끝나면 조각 29 GB 는 지워도 된다. `/app/data` 가 읽기 전용이면 컨테이너 임시 디스크에 풀고 파드와 함께 사라지므로, 관리자에게 `/app/data` 쓰기 권한을 요청하는 편이 낫다. 학생은 공개 모델이라 실행 중 내려받아 `$WORK_ROOT/hf` 에 캐시한다. 토큰 경로(`hf_…` 인자, `/app/data/hf_token.txt`)는 대안으로만 남겨 둔다.
- 신청 창 안에서 이슈를 순서대로 낸다. 컨테이너는 끝나면 삭제되고 `/app/output/` 만 남는다(관리자에게 파일 요청). 리포트는 65,000자까지만 오므로 표준 출력은 요약, 전체 로그는 `/app/output/` 에 쓴다. 격자마다 `results_<cond>_<pool>.zip`(체크포인트·평가·표·그림·로그) 이 만들어지고 라벨은 `labels/<pool>/teacher_labels.parquet` 에 남는다. 관리자에게 zip 6개와 라벨 2개를 요청하면 된다.
- GPU `7` 이면 스크립트가 자동으로 학습 8 병렬·라벨링 4 병렬로 돈다(`NPROC`, `NPROC_LABEL` 로 변경 가능). `1` 이면 순차.

## 결과 표

격자 여섯 개의 결과 표와 교사 기준선은 영문 README 의 [Results](../README.md#results) 절에 있다. 셀마다 `δ1 / AbsRel` 이고 셀 평가가 끝날 때마다 채운다. 숫자는 셀별 로그 `eval_<cond>_<cell>_<pool>_f750_large.log` 에서 가져오며, `tables/table_grid_<cond>_<pool>_f750_large.md` 와 같은 방식으로 계산된다(표에는 신뢰구간이 더해진다). 표를 한 곳에서만 관리하려고 여기에 옮겨 적지 않는다.

평가 세트는 도메인별로 나눠 판정한다(2026-09-29 추가). 실내 풀은 iBims-1·NYUv2, 주행 풀은 KITTI-HO·DDAD, 혼합 풀은 네 세트 모두로 판정하고, 다른 도메인 열은 도메인 이동 결과로만 보고한다. ETH3D 는 모든 풀에 참고로 보고한다. 모든 세트의 GT 는 카메라 중심까지의 유클리드 거리이고, 주행 두 세트는 교사 논문값 비교용으로 z 깊이도 함께 저장한다. 두 주행 세트는 결과 zip 의 어댑터로 로컬에서 평가하므로 다른 열보다 늦게 채워진다.

KITTI-HO(`experiments/40_build_kitti_heldout.py`)는 주행 번호가 아니라 **장소 단위**로 풀과 분리한다. 주행 번호만 빼면 두 가지 겹침이 남기 때문이다. ① 캠퍼스 주행(`2011_09_28`)은 번호만 다를 뿐 같은 장소를 찍는다 — 안 쓴 캠퍼스 주행 50개에서 1장씩 뽑은 초안은 50장 중 19장이 풀 이미지와 같았다(32×32 상관 > 0.9). 그래서 캠퍼스 주행 81개를 모두 뺀다. ② 풀에 들어 있는 KITTI 2012 이미지는 raw 주행에서 잘라 온 것인데 주행 매핑이 공개되어 있지 않다. 그래서 남은 주행의 5프레임마다 풀의 KITTI 이미지 전체와 비교해(dHash 거리 ≤ 10 후 상관 > 0.9), 겹친 프레임 앞뒤 50프레임(5초)을 뺀다. 남은 것은 어느 풀도 쓰지 않고 KITTI 2015 학습 영상의 원본도 아닌 도시·주거·도로 주행 12개이고, 여기서 200장(주행 1초당 최대 1장, 시드 0) × 이미지당 10픽셀(0 < z ≤ 80 m, 테두리 10 px 제외)을 뽑는다. `experiments/42_leak_check.py` 가 완성된 세트에 같은 비교를 독립적으로 다시 돌린다. DDAD 는 val 50장면에서 250장 × 10픽셀을 만든다(준비 중).

교사(DepthLM 12B) 기준선은 이미 채워져 있다. 학생이 채점되는 것과 똑같은 픽셀에, 똑같은 δ1·AbsRel 정의와 똑같은 이미지 군집 부트스트랩으로 쟀다. 중간값 보정만 다르다. 교사는 소수 두 자리로 답하니 +0.005, 학생은 한 자리라 +0.05 다.

## 실험 목록 (6 작업)

| 작업 | POOL | COND | 내용 | 상태 |
|---|---|---|---|---|
| 1 | indoor | soft | 실내 풀, 분포(KL) 증류, 8셀 | 라벨 포함 |
| 2 | outdoor | soft | 주행 풀, 분포 증류, 8셀 | 라벨 포함 |
| 3 | mixed | soft | 실내 50 / 주행 50 풀, 분포 증류, 8셀 | 포함 (로컬에서도 진행 중) |
| 4 | indoor | hard | 실내 풀, greedy(CE) 증류 | 라벨 포함 |
| 5 | outdoor | hard | 주행 풀, greedy 증류 | 라벨 포함 |
| 6 | mixed | hard | 혼합 풀, greedy 증류 | 포함 |

주행 풀의 장면 509개는 실제 장소 수보다 많게 세어져 있다. 장면 집계가 KITTI 2012·2015 이미지를 한 장씩 별도 장면으로 세는데, 이 이미지들은 raw 주행에서 잘라 온 것이라 outdoor 풀의 788장 중 249장(KITTI 2015 165장, KITTI 2012 84장)이 풀에 함께 들어 있는 raw·depth-selection 프레임과 같은 장소다(dHash 거리 ≤ 10, 상관 > 0.9). mixed 풀은 788장 중 176장. 캠퍼스 주행도 한 장소를 여러 주행 번호로 찍어 반복을 더한다. 평가 세트로 새는 것은 아니지만, 주행 풀에서는 이미지 축 N 을 늘려도 장면 수가 말하는 것보다 새 장소가 적게 늘어나므로 N·k 비교의 한계로 보고한다.

풀 v5(2026-09-29, 실외 풀만): 거의 같은 이미지를 순서 맨 뒤로 보냈다(`experiments/07_dedup_pool_order.py`, 보고서 `pools/outdoor/dedup_report.md`). 순서대로 훑으며 이미 남긴 이미지 중 dHash 거리 ≤ 10 이고 32×32 회색조 상관 > 0.9 인 것이 있으면 뒤로 보낸다. DepthLM 도 "아주 비슷한 영상 프레임"은 도움이 안 된다며 일부만 썼는데 규칙은 밝히지 않았다 — 이것은 그 단계를 명시한 버전이다. 실외 이미지 6,400장 중 1,365장이 뒤로 갔다(raw 893장 — 대부분 정차·저속 중, KITTI 2015 195장·KITTI 2012 146장 — 0.1초 간격 `_10`/`_11` 쌍을 둘 다 넣었던 것, depth-selection 131장). 앞 N장 안의 서로 다른 이미지 수는 N = 400 / 1,600 / 6,400 에서 372 / 1,130 / 5,035 → 400 / 1,600 / 5,035 가 되어, 이미지를 많이 쓰는 셀이 복사본 때문에 손해 보지 않는다. 이미지 집합·픽셀 좌표·N = 6,400 셀은 그대로이고, 앞 1,600장에 새로 들어온 이미지의 5,640 px 만 교사 라벨이 새로 필요하다(로컬에서 생성 중). **이 라벨을 커밋하기 전에는 실외 격자를 H200 에 요청하지 않는다** (run.sh 도 라벨이 모자라면 학습을 거부한다). 같은 규칙으로 실내 풀에는 중복이 없다. 혼합 풀(N = 1,600 에서 중복 13 %)은 soft 격자를 이미 학습해서 당분간 지금 순서를 유지한다.

풀 v4(09-23, NYUv2 평가 200장의 195개 방을 장면 단위로 제외. 혼합 146장·실내 333장을 같은 자리에서 교체, `pools/*/pool_v4_report.md`): mixed 6,400장/3,684장면(실내 50·주행 50, 라벨 43,640 px 포함 + 교체분 1,160 px 는 파드에서), indoor 6,400장/5,674장면(새 이미지 205장은 추가 팩 `depthlm_distill_data_extra.tar`), outdoor 6,400장/509장면(주행은 장면 수가 509에서 포화 → N 축 상단은 같은 장면의 프레임 추가, 한계로 명시). 격자 8셀: 이미지 수 N ∈ {400, 1600, 6400} × 이미지당 픽셀 k ∈ {1, 4, 16}, N·k ≤ 25,600. 셀당 2 epoch, LoRA r16, 학생 입력 초점 750.
예상 시간(RTX PRO 4500 기준 0.46 s/step): 작업당 학습 ≈ 19 h + 평가 ≈ 9 h. H200 은 이보다 짧을 것으로 예상(실측 필요).

## 환경

- Python ≥ 3.10, `pip install -r requirements.txt` (torch 는 CUDA 에 맞는 빌드로; transformers 5.16.1, peft ≥ 0.20 고정)
- 모델: `Qwen/Qwen2.5-VL-3B-Instruct` (Apache-2.0, 7.5 GB, 자동 다운로드). 교사 `facebook/DepthLM` 은 이 저장소의 학습·평가에서는 **불필요** (라벨이 포함됨).
- 격자 작업은 HF_TOKEN 이 필요 없다(학생 모델 Apache-2.0). 라벨링 작업만 교사(gated) 다운로드에 읽기 전용 토큰이 필요하다.
- 기본 이미지: 양식의 `pytorch/pytorch:latest`. Docker Hub 이미지 그대로(torch 2.2.1, py3.10)에서 스모크 통과 확인(09-23).
- 데이터: `data/pool/…` (풀 이미지), `data/eval/{ibims1,nyuv2,eth3d}/…` (평가). `DATA_ROOT` 로 위치 변경 가능.
